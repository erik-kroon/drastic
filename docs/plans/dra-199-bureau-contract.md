# DRA-199 bureau obligations contract

Scope: use the application-owned Effect clock for bureau freshness. The dedicated E2E Worker entrypoint (`src/runtime/e2e.ts`, configured only by `tests/support/e2e.wrangler.jsonc`) accepts `x-openerp-test-now` as a canonical UTC instant; the production entrypoint (`src/runtime/cloudflare.ts`) always refuses the header, regardless of bindings. The normal Wrangler configuration and Alchemy deployment both select the production entrypoint. Deploying the test-specific config manually would bypass this deployment convention and must be prohibited by release controls. The test pin is request-scoped, not a process/database clock change. Keep coverage partial/unknown unless supported records prove more.

Failure cases: production accepts a pinned clock; either workerd or native browser E2E harness ignores the pin; a self-host production Bun process accepts the pin; E2E changes worker or database wall clocks; invalid instants are accepted; stale source metadata appears current; a missing due date is guessed; non-obligation evidence is promoted to an obligation; duplicate sources duplicate an obligation; partial source coverage is presented as complete. Native E2E must remain loopback-only with disposable runtime configuration; production self-host never imports the E2E entrypoint.

Acceptance: real PostgreSQL E2E proves the application refuses a test clock in the production Worker, pins the instant to 2 October 2026 08:54 Europe/Stockholm in both workerd and native Bun browser harnesses, and marks a supplier invoice stale after its revision is older than 24 hours. The request-scoped clock changes neither PostgreSQL time nor global process time. Investigate current undated sources; preserve unknown if an actual obligation source can lack a due date, otherwise record the owner decision that no such source is currently released. Write a repeatable artifact.

## Due-date owner decision

The registered supplier invoice is the only source currently admitted into bureau obligations. Its create and revision contracts require a civil `dueOn` date, so every accepted invoice obligation has a date. Tax-account statements and events are accounting observations (`occurredOn`), not admitted payment obligations with a legal due date; an agreement without payment terms is not a released obligation source. Neither may be converted into an obligation or assigned a guessed due date. No current bureau-obligation source can legitimately lack a due date. The nullable/unknown output remains conservative for future sources; no artificial missing-date row is created.

Coverage remains `partial` when registered supplier invoices exist and `unknown` when none do, because unregistered debts and other obligations are not verified. `freshness` compares the current invoice revision's retained creation instant to the application clock with a 24-hour threshold. It describes revision age, not provider or company completeness.

## Bureau portfolio contract

Scope: extend the existing firm portfolio read and `firm_get_portfolio` capability, with authorized HTTP and MCP access to the same operation. A provisioned firm member may use their existing API credential; it requires active firm membership and current book membership for each visible client. A standalone agent-only credential remains refused; this is not OAuth onboarding or general agent delegation. Browser sessions remain supported for humans, without impersonation or changes to human-only firm mutations. Per client, report open work by kind across all periods, registered supplier obligations and nearest known due date, retained unknown outcomes only where an owner supplies them, assigned accountant and last known activity. Summarize needs-today across accessible clients. Missing source data stays labelled unknown; no inferred dates or complete coverage. White-labelling is a product decision, not part of this read.

Failure cases: credential gains firm-only or cross-book accounting access; removed/inactive member still sees clients; a latest-period filter hides older work; a 50-item page silently truncates counts; unknown outcomes are invented or omitted while marked complete; an undated obligation gets a guessed due date; activity from another book leaks; pending access requests become client facts; firm mutation is exposed to agents. Acceptance: real PostgreSQL E2E exercises two books with asymmetric delegated access, cross-period work and an actual due-date source; shared HTTP/MCP results agree, authority refusals hold, and artifacts show counts, deadlines, coverage and activity. Run MCP transport and eval checks before acceptance.

Portfolio result: the read lists exact canonical attention counts by kind over every period, not only the 50-item page. `lastActivityAt` is labelled `canonical_attention_only`, not all book activity. `unknownOutcomes` includes retained unreconciled legal-delivery provider attempts only and says so; a reconciled attempt disappears. Nearest known deadline is the earliest outstanding stored due date (including overdue first), excluding known settled amounts and retaining an unknown residual; no date is inferred. Needs-today uses the Europe/Stockholm civil date for stored instant deadlines. The ordinary firm screen remains human-only; only the portfolio read accepts the provisioned member credential. The portfolio output is an interval of separately authorized owner reads, not an atomic multi-book snapshot.

Portfolio verification on disposable PostgreSQL/workerd: `bunx vitest run apps/api/tests/firm-portfolio.e2e.test.ts` (2/2), `bun run test:mcp` (3/3), `bun run test:mcp:eval` (pinned Luna eval, 1/1 suite), `bunx vitest run apps/api/tests/mcp-authority.e2e.test.ts` (7/7), `bun run check:changed:full`, `bun run check:owners`, and `git diff --check` passed. Evidence: `test-results/e2e/firm-portfolio.json`, `test-results/e2e/results.json`, and the retained `test-results/mcpjam/480362f3-4623-4280-be39-142df8317877/` eval directory. The actual bearer MCP catalog has 426 tools (299 read, 72 prepare, 21 approved-execute, 34 other); Accounted advertises 150+, which is a claim, not a measured parity comparison. OAuth onboarding and production qualification remain unverified.

## Results and use

The focused real-PostgreSQL/workerd E2E (`bunx vitest run apps/api/tests/bureau-obligations.e2e.test.ts`) checks that the production entrypoint returns `403 Forbidden` to a pinned request even when supplied a test-like binding. The separate E2E entrypoint pins `2026-10-02T06:54:00.000Z` (2 October 2026, 08:54 Europe/Stockholm) and verifies `checkedAt`; this historical pin is not asserted stale for an invoice registered at the actual run time. The test reads an unmodified retained invoice through HTTP, pins a second request 48 hours after that baseline `checkedAt`, and verifies the same invoice and source evidence become stale without changing the recorded timestamp, due date or outstanding amount. Malformed instants fail. Neither the E2E nor production runtime changes PostgreSQL, Worker or process wall time; no immutable record or trigger is modified. The test also starts the isolated native Bun browser API against disposable PostgreSQL, observes the same pinned `checkedAt`, and writes `test-results/e2e/native-clock.json` alongside `production-clock-refusal.json`, `bureau-obligations.json`, `manifest.json`, `results.json` and `source-integrity.json`. Demo seeds may send the header to a test Worker or the synthetic native browser API, never to either production entrypoint. `infra/self-host/Dockerfile.dockerignore` excludes the E2E entrypoint, native browser script and test config from the self-host image context; Docker is unavailable locally, so final image exclusion is not yet verified on an engine. Manual deployment of the test entrypoint outside the standard Alchemy/Wrangler paths still needs release controls. The header affects only reads that use the application Effect clock; it does not rewrite timestamps stored by PostgreSQL or other code paths.
