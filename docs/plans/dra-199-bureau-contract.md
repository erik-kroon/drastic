# DRA-199 bureau obligations contract

Scope: use the application-owned Effect clock for bureau freshness. The dedicated E2E Worker entrypoint (`src/runtime/e2e.ts`, configured only by `tests/support/e2e.wrangler.jsonc`) accepts `x-openerp-test-now` as a canonical UTC instant; the production entrypoint (`src/runtime/cloudflare.ts`) always refuses the header, regardless of bindings. The normal Wrangler configuration and Alchemy deployment both select the production entrypoint. Deploying the test-specific config manually would bypass this deployment convention and must be prohibited by release controls. The test pin is request-scoped, not a process/database clock change. Keep coverage partial/unknown unless supported records prove more.

Failure cases: production accepts a pinned clock; E2E changes worker or database wall clocks; invalid instants are accepted; stale source metadata appears current; a missing due date is guessed; non-obligation evidence is promoted to an obligation; duplicate sources duplicate an obligation; partial source coverage is presented as complete.

Acceptance: real PostgreSQL E2E proves the application refuses a test clock in production mode, pins the instant to 2 October 2026 08:54 Europe/Stockholm, and marks a supplier invoice stale after its revision is older than 24 hours. The request-scoped clock changes neither PostgreSQL time nor global process time. Investigate current undated sources; preserve unknown if an actual obligation source can lack a due date, otherwise record the owner decision that no such source is currently released. Write a repeatable artifact.

## Due-date owner decision

The registered supplier invoice is the only source currently admitted into bureau obligations. Its create and revision contracts require a civil `dueOn` date, so every accepted invoice obligation has a date. Tax-account statements and events are accounting observations (`occurredOn`), not admitted payment obligations with a legal due date; an agreement without payment terms is not a released obligation source. Neither may be converted into an obligation or assigned a guessed due date. No current bureau-obligation source can legitimately lack a due date. The nullable/unknown output remains conservative for future sources; no artificial missing-date row is created.

Coverage remains `partial` when registered supplier invoices exist and `unknown` when none do, because unregistered debts and other obligations are not verified. `freshness` compares the current invoice revision's retained creation instant to the application clock with a 24-hour threshold. It describes revision age, not provider or company completeness.

## Results and use

The focused real-PostgreSQL/workerd E2E (`bunx vitest run apps/api/tests/bureau-obligations.e2e.test.ts`) checks that the production entrypoint returns `403 Forbidden` to a pinned request even when supplied a test-like binding. The separate E2E entrypoint pins `2026-10-02T06:54:00.000Z` (2 October 2026, 08:54 Europe/Stockholm) and verifies `checkedAt`; this historical pin is not asserted stale for an invoice registered at the actual run time. The test reads an unmodified retained invoice through HTTP, pins a second request 48 hours after that baseline `checkedAt`, and verifies the same invoice and source evidence become stale without changing the recorded timestamp, due date or outstanding amount. Malformed instants fail. Neither the E2E nor production runtime changes PostgreSQL, Worker or process wall time; no immutable record or trigger is modified. The test writes `test-results/e2e/production-clock-refusal.json`, `bureau-obligations.json`, `manifest.json`, `results.json` and `source-integrity.json`. Demo seeds may send the header to an E2E Worker, never to the production Worker. The header affects only reads that use the application Effect clock; it does not rewrite timestamps stored by PostgreSQL or other code paths.
