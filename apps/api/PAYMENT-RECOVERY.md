# PAY-1 payment preparation and external outcome boundary

Status: implemented in source; no bank-provider acceptance, real company activation, or financial runtime proof.

`7900-supplier-payment-recovery.sql` preserves the existing offline `pain.001.001.03` preview and immutable export. A scoped keyset eligibility page covers **every registered supplier invoice** in a book, including excluded invoices, with the exact live outstanding amount, allocation version and exclusion reasons. It does not claim unregistered supplier documents, historical cutoffs or a stable multi-page snapshot. Restart discovery after changes.

The operator proposes a payee name/IBAN/BIC backed by retained evidence. A *different* authorized operator must confirm the same proposal digest and evidence. Verification binds the supplier identity revision and exact account fields. A new payee proposal or supplier revision invalidates older verification for future previews/exports; previously exported bytes remain immutable and reserved. Old pre-migration previews without verification cannot be exported through the new check. A preview is rechecked under the book lock when exported. The verification is a recorded independent internal check, **not** provider account-owner confirmation or bank acceptance.

XML uses the existing synthetic `pain.001.001.03` serialization, escaped fields and IBAN check digits. This is **not** an ISO XSD/provider certification. The profile remains `synthetic-offline-pain001-v1`; exported bytes retain `bankCompatible: false`. Do not upload the file as a production payment without an approved provider profile and external acceptance (D-10). The procedure neither calls a bank nor allocates a posted bank payment.

Reported outcomes append immutable same-book evidence and exported SHA-256: `unknown`, `reported_accepted`, `reported_settled`, `reported_rejected`. `externalStatus` reports `not_exported`/`exported` before any outcome. Later reports cannot overwrite a reported settled or rejected status; a reported accepted status cannot turn into rejected without manual reconciliation. All reported outcomes retain `bankVerified: false`, `paid: false` and `allocationCreated: false`: an operator's report is not a verified provider webhook, a bank statement or a posted settlement. Exports remain reserved even after rejection; payment replacement and release require a separate, reviewed no-execution resolution. Recover a lost response using the **same idempotency key** and read the preview, immutable exported bytes and outcome history. Do not make a new export to probe an unknown outcome.

REST wiring lives in `packages/contracts/src/supplier-payment-batches.ts`, `apps/api/src/transport/http/routes/supplier-payment-batches.ts`, and `apps/api/src/db/statements/supplier-payment-batches.ts`. Root owns the shared API composition, query-dispatch and capability maps; these additions need root wiring before the new REST operations work. See the child handoff for exact keys. No new tests or fixtures were added (D-09).

A fresh isolated local PostgreSQL 17 database applied the migration; the final changed read-function definition also compiled there. A rerun was blocked by a concurrent edit to migration `7710-sie-financial-run.sql`, not by this payment migration. These checks show SQL definition acceptance only. Type checks and lint are static checks, not payment behavior, XML schema compatibility, provider acknowledgement or concurrency proof. Real application and bank outcome behavior remain unverified.
